# OpenTodo v0.0.1: Desktop-first todo app

Implementation target for review, not implemented. Intended release milestone: `v0.0.1`.

This is the canonical implementation spec for the desktop-first direction. It carries forward the todo workflows in [PRD #1](https://github.com/raeperd/opentodo/issues/1) and supersedes conflicting architecture and execution instructions in [PROMPT.md](../PROMPT.md) and the historical [issue plans](../issues/). Use the local IDs below until desktop implementation issues are published; the numbered plan filenames are not GitHub issue IDs.

## Problem

OpenTodo needs to work as a personal desktop todo app without an account, internet connection, or hosted service. The repository has a pnpm workspace, a static SvelteKit UI, an Electron window, and Effect server/API placeholders. Task storage and user workflows are not implemented.

## Intended outcome

On macOS, launch OpenTodo, capture and organize tasks with a dense dark interface, and use the keyboard for everyday actions. Tasks remain on this computer across window closes, app restarts, and network outages. Build the first complete workflow as create task → quit → reopen → task persists, then extend it to the remaining acceptance scenarios.

## Use cases and acceptance scenarios

Each row owns one acceptance scenario; edge cases remain under that ID. Run persistence assertions after a real app restart, not only a renderer reload.

| ID    | Outcome                                  | Acceptance scenario                                                                                                                                                                                                                                                                                                                          |
| ----- | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OT-01 | Capture a task offline and keep it       | With a fresh application data directory and external network access blocked, launch, create a titled task, wait for saved state, quit, and relaunch; exactly one task returns. Empty or whitespace-only titles create nothing.                                                                                                               |
| OT-02 | Edit a task title inline                 | Edit a saved title, confirm, and relaunch; the new title remains. Escape cancels the draft; rejecting an empty title preserves the saved value.                                                                                                                                                                                              |
| OT-03 | Complete and reopen work                 | Complete an active task; active counts decrease and it appears under Show completed. Reopen it there and relaunch; it is active again with its other fields intact.                                                                                                                                                                          |
| OT-04 | Delete a task deliberately               | Cancel deletion, then confirm it; only the selected task and its tag assignments disappear, and it stays absent after relaunch.                                                                                                                                                                                                              |
| OT-05 | Keep task notes in the detail panel      | Select a task, edit multiline Markdown source, blur to save, close the panel with Escape, and relaunch; the exact text returns. Keyboard focus returns to the originating task when the panel closes.                                                                                                                                        |
| OT-06 | Set, change, and clear due dates         | With a fixed clock and timezone, preview and confirm tomorrow, next Friday at 3pm, and in two hours; verify the resolved values. Set an exact date through the picker, relaunch, then clear it. Invalid input keeps the existing date and offers the picker.                                                                                 |
| OT-07 | Surface urgent tasks                     | Assign none, low, medium, and high priorities to tasks; the current view sorts by its rules below, and values and order remain after relaunch.                                                                                                                                                                                               |
| OT-08 | Organize tasks into projects             | Create and rename a colored project, assign a task, then move it to another project; sidebar membership, counts, and task details agree after relaunch.                                                                                                                                                                                      |
| OT-09 | Remove a project without unintended loss | Cancel project deletion, then choose Keep tasks; the project disappears while its tasks retain dates, tags, priority, and notes without a project. On a separate fixture, choose Delete tasks and confirm; that project and its tasks disappear together.                                                                                    |
| OT-10 | Categorize tasks with reusable tags      | Create colored tags, assign several through autocomplete, filter by one, then rename and recolor it; every assignment reflects the change after relaunch. Removing one assignment leaves the tag and other assignments intact.                                                                                                               |
| OT-11 | Delete a tag without deleting tasks      | Confirm deletion of an assigned tag; it disappears from autocomplete, filters, and all tasks after relaunch, while the tasks remain.                                                                                                                                                                                                         |
| OT-12 | Find work through the sidebar            | Seed undated, overdue, today, future, project, and completed tasks. Navigate Inbox, Today, Upcoming, project, and tag views; membership, ordering, overdue indicators, and active counts follow the rules below. Advance the clock across midnight and verify membership updates.                                                            |
| OT-13 | Arrange tasks manually                   | Drag within one sortable group, then use the keyboard Move up/down actions; both changes persist after relaunch. A filtered reorder preserves hidden tasks' relative order and never changes dates, priorities, or project membership.                                                                                                       |
| OT-14 | Work from the keyboard                   | Use n to draft a task, Enter to save, j/k to move focus, e to edit, and x to complete. These letter shortcuts do not fire while typing or composing text; Tab and visible focus reach every action.                                                                                                                                          |
| OT-15 | Find and act from the command palette    | Open with Cmd+K, fuzzy-search tasks, projects, tags, and actions, select a result, and observe navigation or the requested action. Escape closes the palette and restores focus; no-match results are explicit.                                                                                                                              |
| OT-16 | Understand pending and failed saves      | Delay a real write: the UI updates immediately and indicates pending state. Cause a storage failure: it shows an actionable error, restores confirmed data, and retains editable input for retry. Lose a reply after commit: reload the authoritative snapshot and show the committed change once.                                           |
| OT-17 | Close and reopen the window safely       | With an unsaved draft or pending save, request Close; cancel once, then resolve the save/discard choice. On macOS, reopen through the Dock; saved tasks return in one window. A second app launch focuses that window without starting another database owner.                                                                               |
| OT-18 | Quit without silently losing changes     | Request Quit while editing or saving; Cancel preserves work, Save and quit waits for acknowledgment, and Discard applies only to unsent drafts. After a clean quit, the owned server has exited; relaunch shows every acknowledged write.                                                                                                    |
| OT-19 | Recover from a server crash              | Kill the server before and after a transaction commits. The UI disables writes and retains drafts; Restart reopens the same database and reconciles state without automatically repeating a command. A committed write returns once; an interrupted transaction leaves no partial change.                                                    |
| OT-20 | Preserve data when startup fails         | Launch with an unreadable, invalid, or newer-schema database, and with a fixture whose migration fails; show the failure and data location, preserve the existing database, and never substitute an empty store. | OT-21 | Reject unauthorized local control        | Against the running app, attempt requests without the launch credential, with a wrong credential or browser origin, and from an untrusted IPC sender; each is rejected without changing tasks or exposing database access.                                                                                                                   |
| OT-22 | Use a readable dark desktop interface    | At the supported minimum window size and a larger size, inspect populated and empty views, the detail panel, palette, pending state, and errors; actions remain reachable without overlap, focus is visible, and reduced-motion settings are respected.                                                                                      |

## Implementation decisions

### Stack and ownership

Keep the existing pnpm workspace, Node 24 development runtime, strict TypeScript, Svelte 5, SvelteKit static adapter, Vite, Tailwind CSS, Electron, Effect, oxlint, oxfmt, and Vitest. Read exact versions from the manifests and lockfile. Keep Effect packages aligned and change versions only when an implementation requirement needs it. Add Drizzle with `node:sqlite`, chrono-node, shadcn-svelte components, and Playwright as the owning scenarios require them; pin and verify compatibility then.

The app has three application processes: Electron main, one renderer, and one owned server child. Preload runs with the renderer; shared API definitions are code, not a process. Electron may create its own supporting processes.

| Module         | Runs in                            | Owns                                                                                                                                                      |
| -------------- | ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `apps/desktop` | Electron main and isolated preload | One window, native lifecycle and dialogs, data-directory selection, server startup/shutdown, authenticated API connection, and the narrow renderer bridge |
| `packages/api` | Shared code                        | Browser-safe Effect Schema contracts, request/result types, validation, and typed errors                                                                  |
| `apps/server`  | Electron-owned Node utility child  | Task/project/tag operations, the SQLite connection and migrations, transactions, canonical snapshots, and cleanup                                         |
| `apps/web`     | Electron renderer                  | Ordinary Svelte UI and reactivity, input drafts, optimistic state, navigation, and connection/save status                                                 |

Use Effect for server operations and desktop resource lifetimes, with composition at process entry points. Keep pure calculations and framework UI code in ordinary TypeScript/Svelte. Web imports API definitions, never database or server implementation code.

### Local API and desktop boundary

- Start the server through Electron's `utilityProcess` after app readiness. It uses Electron's bundled Node runtime; a separately installed Node executable is a development prerequisite, not an application runtime dependency. OT-01 must prove the selected Electron/Drizzle/`node:sqlite` combination in the actual child process. [Electron utility processes](https://www.electronjs.org/docs/latest/api/utility-process) provide the child runtime.
- Use Effect RPC over loopback HTTP between Electron main and the child. Bind only to `127.0.0.1` on an ephemeral port. Main supplies a fresh launch credential over the private parent/child channel and retains the authenticated client. Reject browser-origin requests and unauthenticated calls; remote access is outside this release.
- Preload exposes typed task, project, tag, snapshot, and lifecycle capabilities. Main validates the sender and payload before forwarding domain operations. The renderer receives neither the credential nor arbitrary HTTP, IPC, filesystem, SQL, or process access. Keep context isolation, sandboxing, disabled Node integration, a restrictive CSP, and navigation/window restrictions.
- The server validates every command, uses explicit create/update/delete/reorder operations, and returns either committed results or typed validation, missing-record, conflict, or storage errors. A success response means the transaction committed. Completion is an explicit target state, not a retry-sensitive toggle.
- Use client-generated IDs for creations and serialize mutations from the single window. Repeated creation of the same ID cannot create a second record. After each acknowledged mutation, reconcile with a canonical snapshot; sequence snapshots so an older response cannot replace newer state. On renderer reload or reconnect, fetch a fresh snapshot before enabling writes. Do not automatically replay commands whose outcome is unknown.

### Persistence and recovery

- Store one personal database at `app.getPath("userData")/opentodo.sqlite`. Main supplies the absolute location; the server is its only owner. A test launch overrides the data directory before startup. Use the operating-system account as the user boundary; there are no app accounts, user tables, or login screens. The UI remains usable with external network access blocked.
- Use Drizzle's `node:sqlite` driver behind the server's Effect service boundary. Keep synchronous database operations in the child. Drizzle documents this driver in its current RC guidance, so verify the pinned release's exports and transaction API in OT-01 rather than assuming stable-version compatibility. [Drizzle Node SQLite](https://orm.drizzle.team/docs/sqlite/connect-node-sqlite).
- Persist tasks with ID, nonempty trimmed title, Markdown source description, completion state, priority, optional due value, optional project, manual position, and creation/update timestamps. Persist colored projects, colored tags, and unique task/tag assignments with foreign keys. Completion changes neither notes nor organizational fields. Delete/reorder operations spanning several rows are atomic.
- Enable foreign keys, WAL, and durable commits. Keep numbered SQL migrations with the server and record their applied versions. Apply each migration transactionally before serving requests. Create an empty database only on first launch; an existing unreadable database, unsupported newer schema, or failed migration blocks startup without resetting it. No Drizzle Kit dependency is required for this release.
- Optimistic data is visibly pending until acknowledgment. Definite failures restore confirmed state and retain the user's input. An interrupted connection is an unknown outcome: reload the database snapshot before offering retry. Drafts live in the renderer and are not guaranteed to survive a renderer crash or force-quit; acknowledged database writes must survive a process crash.
- Acquire Electron's single-instance lock before starting the server. A second launch activates the existing window. Closing the last window on macOS keeps the app and server available; full Quit stops new writes, resolves unsaved input, drains accepted operations, closes SQLite, and waits for child exit. If saving fails, remain open with Retry/Cancel. If shutdown hangs, offer an explicit Force quit action explaining that pending work may be lost. The child exits when its parent channel closes.
- A server crash shows an error and a user-triggered Restart action; restarting reopens the same database. There is no automatic restart loop or independent background daemon. Startup failures show the database path and a retry action. Preserve user files during every recovery path.

### Todo behavior

- Use a dense dark layout with sidebar navigation, task rows, inline title editing, and a detail panel. Markdown descriptions are plain source in a textarea, saved on blur; rich editing and rendered HTML are outside this release. New-task keyboard actions open a draft and persist only after a valid title is confirmed. Confirm destructive task, project, and tag deletions.
- Priorities are none, low, medium, and high. Inbox contains active tasks without a project or due date. Today contains active tasks due today or overdue. Upcoming contains active future-dated tasks grouped by local calendar day. Project and tag views contain their active members; counts exclude completed tasks. Each view has Show completed so completion is reversible. Search includes completed tasks and opens their details.
- Within Inbox, Today, project, and tag views, sort by priority descending, then manual position, with ID as the final tie-breaker. Upcoming sorts by due day first, then the same rules. Reorder only within a priority group and, in Upcoming, within a due-day group. Use one persisted task order shared across views; a reorder can affect another view. Update the selected visible sequence transactionally while preserving hidden tasks' relative order. Provide keyboard Move up/down actions alongside dragging.
- Deleting a project offers Keep tasks or Delete tasks. Keep tasks clears only project membership, preserving dates and other fields. Undated tasks return to Inbox; dated tasks remain in Today or Upcoming. Deleting a tag removes assignments, not tasks. Renames and color changes apply everywhere through the shared project/tag record.
- Store a due value as absent, a date-only `YYYY-MM-DD`, or a UTC instant when a time is specified. Date-only values keep their calendar date; instants display in the current device timezone. Today and Upcoming use that timezone, and date-only tasks become overdue the next day. Timed tasks become overdue after their instant. Recompute on midnight, wake, and timezone changes.
- Use English chrono-node input with an explicit reference clock and device timezone. Show the resolved date/time before saving; never silently replace a date when parsing fails. Keep an exact date picker and optional time input as the fallback. Explicit past dates are allowed and shown as overdue. Relative phrases resolve once when confirmed. See [chrono-node's parsing reference](https://github.com/wanasit/chrono).
- Scope j/k/x/e/n to the task list when focus is outside inputs, textareas, editable content, and IME composition. Cmd+K opens the palette; Escape closes the topmost edit/panel/palette and restores focus. Provide Tab-accessible equivalents for every action and visible focus indicators. Search tasks, projects, tags, and registered navigation/actions locally; no external search service is needed.

## Testing decisions

### Coverage and controlled boundaries

- Run OT-01 through OT-20 and OT-22 through the actual Electron UI and lifecycle. Run OT-21 against the full running app with unauthorized clients and senders. Use [Playwright Electron](https://playwright.dev/docs/api/class-electron); support is experimental, so pin a compatible version and prove launch, restart, and child cleanup with OT-01 before building shared test infrastructure.
- Keep Electron, preload, the server, Effect RPC, and SQLite real. Control only the reference clock/timezone, native dialog results, and transport/process/filesystem failure conditions. Use temporary data directories and real database files; tests never use a personal database or credentials. For write-failure scenarios, use an unwritable fixture or a controlled error at the filesystem boundary, not mocked domain handlers.
- Vitest tests for date boundaries, search ranking, validation, and ordering supplement the application scenarios. Database integration tests cover constraints, transaction rollback, interrupted writes, and migrations against real SQLite. Renderer-only or mocked API tests do not establish desktop acceptance.
- Cover save rejection, reply loss after commit, renderer reload, server crash, supported schema upgrades, newer schemas, midnight/DST/timezone changes, filtered ordering, and keyboard input suppression under their owning IDs. Test real Electron sandbox/preload settings; automation must not weaken the application's boundary to make tests pass.

### Reproduction and release checks

- Existing commands are `pnpm install --frozen-lockfile`, `pnpm dev` for the web renderer, `pnpm start:desktop` for build-and-launch, and `pnpm test`, `pnpm check`, `pnpm build` for verification. `pnpm dev` alone is not a desktop acceptance run. The application is currently a foundation, so these commands do not yet exercise the scenarios above.
- The first acceptance-test implementation must add documented commands for the Electron suite, a single OT-ID, and visible step-through debugging. Report exact commands after they exist; supply isolated fixture setup and cleanup. Save screenshots, Playwright traces, and redacted desktop/server logs on failure, with the scenario ID and Electron/Node/dependency versions.
- Retain the existing Linux checks and add a macOS job for all desktop scenarios. Current CI runs tests, formatting, lint, types, and builds on Linux and skips changes confined to `docs/`; desktop CI is implementation work. Use no network services, personal credentials, or paid APIs in acceptance tests.
- Release `v0.0.1` only when all 22 scenarios and their required failure variants pass, required CI is green, and a manual macOS check confirms Dock activation, native dialogs, keyboard focus, and the dark layout. Record an offline create/edit/quit/relaunch run against disposable data. This is a release runnable from source; installers, signing, and automatic updates are deferred.

## Implementation workflow

1. Start with OT-01. Add the shared contracts, owned child, real database, minimal UI, and Electron test only as needed to prove persistence across a full quit and relaunch.
2. Establish save/error behavior and lifecycle coverage alongside the operations they protect. Then extend task editing/completion, organization and dates, views/reordering, keyboard controls, and visual checks. Publish implementation issues only when requested, grouped under the intended `v0.0.1` milestone.
3. For each scenario, observe the behavioral test failure, implement the smallest passing change, and refactor with tests green. Preserve already-passing scenarios. Migrations and API changes include their failure and recovery coverage.
4. Each implementation PR links its issue and this spec, names covered OT-IDs, and records rerun commands and verification. Replace local IDs with real issue links when issues are published, preserving scenario ownership. Related scenarios may share a PR; there is no fixed PR count.

## Out of scope

- Cloud accounts, Google OAuth, synchronization, collaboration, hosted web deployment, PWA/mobile clients, and a remote/public API.
- CLI, MCP, Pi or other agent integrations, calendar sync, reminders, recurring tasks, subtasks, boards, and global quick-add shortcuts.
- Multiple windows or databases, automatic crash restart, encrypted storage, backup/export/import UI, and recovery of unsaved drafts after force-quit. Local database persistence does not provide a backup of the device.
- Windows/Linux desktop acceptance, installers, signing/notarization, automatic updates, light theme, and a rich Markdown editor.
